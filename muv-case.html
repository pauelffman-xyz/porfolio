MUV operates a ride-hailing platform where passengers and drivers interact through a real-time system with multiple states and edge cases.

The existing experience showed friction in key moments — onboarding, ride request and status feedback. This generated confusion, slower time to first ride and higher cognitive load.

Key Design Decisions
Decision 01
Explicit ride state feedback
The interface always communicates the current backend state — even during waiting. Eliminates anxiety through information.
Decision 02
Color system 60/30/10
60% neutral · 30% primary orange · 10% secondary navy. The previous system lacked balance — rebuilt for harmony.
Decision 03
Component-driven layout
Every screen built from reusable components. Typography, icons, tokens, motion, photography — all part of the system.
Decision 04
Skeleton loading state
Communicates that something is happening — reduces perceived wait time and eliminates confusion during availability calculation.
Decision 05
"Recomendado" preselection
Preselecting the Económico option reduces decisional friction. User can confirm in one tap. Business steers toward preferred category.
Decision 06
Ueno Bank rebate always visible
40% con crédito · 20% con débito — visible on the category screen. Ecosystem integration as competitive advantage.
Design System · Components

Built to scale.
Documented to ship.

Every component was designed with clear states, real content and system logic. The design system ensures consistency across the passenger app — from the first trip request to the post-ride review.

01 Driver Card · States

The driver card communicates all key information during the matching and in-trip states. Two visual variants adapt based on the ride phase — waiting for driver confirmation (with free-cancellation countdown) and in-transit (with live ETA).

02 Category Card · States

03 Push Notifications · Real-time States

Push notifications communicate ride state changes in real time — even when the app is backgrounded. Each state has a distinct message and visual hierarchy that reduces user anxiety during waiting periods.

Searching
"Esperando confirmación del conductor... Ampliando radio de búsqueda" — animated progress bar communicates active search.
In transit
"10 min para llegar a la parada · Juan empezó tu viaje" — car icon moves along progress bar with real ETA.
Permission request
"¿Querés recibir alertas del viaje en tiempo real?" — surfaces at the right moment to maximize opt-in rate.

01
State-driven

Every component maps directly to a backend state. No ambiguity between UI and system logic.

02
Information hierarchy

Critical info (driver, ETA, plate) is always prominent. Secondary data (payment, route) is contextual.

03
Reusable by design

Every component supports multiple states via props — not separate components. Scalable from day one.

Learnings
Learning 01
State management IS the design
Mapping every possible state before opening Figma saved weeks of rework and produced a more coherent experience end-to-end.
Learning 02
Test direction, not detail
The map vs photo test wasn't about visual preference — it was about mental model. Users think spatially about transportation.
Learning 03
Visual QA in Dev Mode = collaboration
Annotating design vs implementation in Figma Dev Mode turned QA from confrontation into collaboration. Measurable quality improvement.
The core principle
"Simplicity is the hardest design decision."
Every stakeholder wanted to add. Every user wanted less. Holding the line — and proving it with data — is a design skill as important as any visual craft. The numbers proved it right.
